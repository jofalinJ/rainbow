# Face attendance provider research

Verified against primary sources on **15 October 2026**. This is engineering research and a production-readiness aid; deployment and the employer's policy/legal decisions are separate steps.

## Recommended provider and browser integration

Use **Amazon Rekognition Face Liveness** followed by **Rekognition collection matching bounded to the employee whose identity has already been claimed**. Liveness is a real, streamed challenge/response service; a camera selfie or local face detector alone cannot replace it. AWS states that liveness remains probabilistic and should be combined with other factors. [AWS service overview](https://docs.aws.amazon.com/rekognition/latest/dg/face-liveness.html)

Use **Mumbai (`ap-south-1`)** for both liveness creation/streaming and image matching. AWS currently lists Mumbai among supported Face Liveness regions, with `streaming-rekognition.ap-south-1.amazonaws.com` as its streaming endpoint. [Supported regions](https://docs.aws.amazon.com/rekognition/latest/dg/face-liveness-faq.html), [regional endpoints](https://docs.aws.amazon.com/general/latest/gr/rekognition.html)

The existing vanilla page can mount one bundled React island. The supported web component is `FaceLivenessDetectorCore` from `@aws-amplify/ui-react-liveness`, receiving `sessionId`, `region`, `onAnalysisComplete`, `onError`, and `config: { credentialProvider }`. A custom credentials provider can obtain STS credentials; Cognito need not replace Supabase authentication. The provider is called once at the beginning and has no refresh during the flow. The completion callback must ask the backend to verify results; browser callbacks never authorize an attendance write. [Amplify React integration](https://ui.docs.amplify.aws/react/connected-components/liveness)

The AWS-maintained package currently publishes stable **3.7.0**. Pin and bundle a reviewed version, keep its lockfile, and avoid a floating production CDN import. AWS requires security-sensitive SDK updates within its release windows, so ongoing maintenance is needed. [Official AWS npm package](https://www.npmjs.com/package/%40aws-amplify/ui-react-liveness?activeTab=versions), [AWS update policy](https://docs.aws.amazon.com/rekognition/latest/dg/face-liveness-update-guidelines.html)

Android Chrome is suitable when it meets AWS's requirements: a real color front camera recording at least 480×640 and 15 fps, 60 Hz display, screen at least four inches, and sufficient bandwidth. AWS supports the latest three major browser versions. Test the actual shop device in portrait mode, including camera denial, dim light, slow network, and interruption recovery. [User-side requirements](https://docs.aws.amazon.com/rekognition/latest/dg/face-liveness-requirements.html), [Amplify errors](https://ui.docs.amplify.aws/react/connected-components/liveness)

## Server-owned flow and bounded verification

The following is the proposed application design, inferred from the documented APIs:

1. Authenticate staff/admin/kiosk using the site's server-verifiable identity. Resolve employee permissions, enrollment state, consent version, purpose, action, device, and a unique attempt identifier on the backend.
2. Create a fresh `CreateFaceLivenessSession` and save its association with that attempt. Each session is single-use and expires three minutes after creation; retries require a new session. Omit `OutputConfig` and explicitly set `Settings.AuditImagesLimit` to `0`, returning reference bytes to the backend rather than persisting images in S3. [CreateFaceLivenessSession](https://docs.aws.amazon.com/rekognition/latest/APIReference/API_CreateFaceLivenessSession.html)
3. Return the session ID, region, and narrowly scoped temporary credentials to the authorized browser. Browser role: only `rekognition:StartFaceLivenessSession` on `*`, no create/results/index/search/delete permissions. The backend may use STS `AssumeRole` with a restrictive inline session policy; its minimum duration is **900 seconds**, so do not configure a three-minute STS duration. [Amplify IAM example](https://ui.docs.amplify.aws/react/connected-components/liveness), [STS AssumeRole](https://docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRole.html)
4. After the challenge, the backend fetches results for the stored session, requires `SUCCEEDED` and its configured liveness threshold, and uses only AWS's returned reference image. Do not accept a client-posted substitute image, score, matching employee, or success flag.
5. For enrollment, use three independently completed liveness sessions. Index only high-quality, single-face reference images into a new opaque employee/enrollment-version collection. `IndexFaces` supports `MaxFaces: 1`, `QualityFilter: HIGH`, face metadata and unindexed-face reasons. Detect/reject multiple faces before indexing; `MaxFaces: 1` alone selects one face rather than proving there was exactly one. [IndexFaces](https://docs.aws.amazon.com/rekognition/latest/APIReference/API_IndexFaces.html)
6. Compare later enrollment samples to the first sample in that new collection so an enrollment cannot combine different people. Activate only after the required sample count succeeds. Treat duplicate sample/session reuse as invalid and delete abandoned enrollment collections through a scheduled cleanup path.
7. For attendance, load the selected employee's active collection on the backend and call `SearchFacesByImage` only against that collection. It searches the largest input face and accepts `FaceMatchThreshold`, `MaxFaces`, and `QualityFilter`. Reject an absent match. Never use one collection containing the whole staff roster or accept a collection identifier supplied by the browser. This is claimed-identity verification against a few samples of one person; the API internally searches that person's samples. [SearchFacesByImage](https://docs.aws.amazon.com/rekognition/latest/APIReference/API_SearchFacesByImage.html)
8. The backend alone consumes the attempt and writes the attendance event atomically, using server time and server-derived action. A unique attempt/event constraint must make replay and concurrent completion harmless. Fail closed for liveness, quality, matching, expiry, unavailable enrollment, or provider errors. Provide the authorized manual attendance path for accessibility and service outages.

Three samples, the sample-consistency gate, opaque collections, atomic writes, and fallback routing above are application choices rather than AWS guarantees. Multi-sample enrollment should use neutral expression, bright/sharp color images, visible eyes and modest pose changes; a liveness reference frame may be frontal even if the user began from another pose. AWS documents pose/quality guidance. [Image recommendations](https://docs.aws.amazon.com/rekognition/latest/dg/recommendations-facial-input-images.html)

Use separately configurable liveness and similarity thresholds. A value such as 99 is a starting policy requiring validation, not an accuracy percentage or an AWS attendance recommendation. Pilot on the actual staff, devices, and lighting, including legitimate nonmatches and authorized spoof testing, before enabling payroll consequences. AWS explicitly requires case-specific calibration. [Similarity thresholds](https://docs.aws.amazon.com/rekognition/latest/dg/thresholds-collections.html), [Face Liveness service card](https://docs.aws.amazon.com/ai/responsible-ai/rekognition-face-liveness/overview.html)

## Data protection and deletion

Rekognition collections store encrypted facial feature vectors. The application needs only opaque provider collection/face identifiers and enrollment metadata; it need not retain raw enrollment photos in Supabase or object storage. Liveness session data is encrypted, HTTPS protects API transport, and an optional customer KMS key can encrypt liveness reference/audit images. [AWS encryption documentation](https://docs.aws.amazon.com/rekognition/latest/dg/security-data-encryption.html)

**Provider setup requirement:** AWS's image/video input content can be retained and used for service improvement by default. Before any real enrollment, apply and verify an effective **AWS Organizations AI services opt-out policy** for Rekognition. This is required to support the intended no-default-photo-retention claim. Choosing Mumbai alone does not disable service-improvement retention. [AWS opt-out behavior](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_manage_policies_ai-opt-out.html), [policy syntax and effective-policy guidance](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_manage_policies_ai-opt-out_syntax.html?icmpid=docs_orgs_console)

Keep reference bytes only in request memory, never logs/analytics/error payloads; omit S3 output; avoid audit frames by default. Session expiry removes access to session data, but does not substitute for verifying the account opt-out policy. On withdrawal, reset or termination, disable verification immediately, delete obsolete provider collections, and audit the deletion with identifiers and status only. Store consent/attendance/security records under an employer-approved retention schedule separately from templates. A future change in legal retention requirements needs policy review before changing raw-image handling.

## India production policy review

As of the research date, do not describe all DPDP obligations as already enforceable. The official commencement notification places substantive Act sections 3–17 and section 44(2) eighteen months after November 2025 Gazette publication, in May 2027. The final Rules similarly phase Rules 3 and 5–16 to eighteen months. Section 44(2) is the amendment that omits IT Act section 43A. [Official commencement notification, G.S.R. 843(E)](https://www.meity.gov.in/static/uploads/2025/11/c56ceae6c383460ca69577428d36828b.pdf), [official DPDP Act](https://www.meity.gov.in/static/uploads/2024/02/Digital-Personal-Data-Protection-Act-2023.pdf), [official DPDP Rules](https://www.meity.gov.in/static/uploads/2025/11/53450e6e5dc0bfa85ebd78686cadad39.pdf)

The existing SPDI framework explicitly includes facial biometric information. Its rules call for an accessible privacy policy; purpose-specific consent before collection; necessary collection for a lawful purpose; disclosure of recipients and retaining agency; correction and withdrawal; limited retention; grievance contact; protected third-party transfer; and documented security measures. For this project, publish the employer/processor details and obtain affirmative electronic consent before starting the camera; record notice version, time, employee, and operator. [Government-hosted 2011 Gazette, G.S.R. 313(E), pages 7–11](https://emb.mes.gov.in/Common/help/gsr3_10511.pdf)

The Government's clarification expressly includes electronic communication as consent. The employer should settle the notice language, processor contract, grievance owner, retention, withdrawal/deletion policy, and manual alternative before enrollment. [Government clarification, 24 August 2011](https://www.pib.gov.in/newsite/erelcontent.aspx?lang=2&reg=48&relid=74990)

For future readiness, DPDP section 7(i) includes employment among legitimate uses, while section 8 maintains safeguards and accountability. This does not decide whether compulsory biometrics are appropriate for a particular employer; keep the present consent/manual-option design pending qualified review. [Official Act, sections 7–8](https://www.meity.gov.in/static/uploads/2024/02/Digital-Personal-Data-Protection-Act-2023.pdf)

Final Rules 6–8 address access/security records, breach reporting and a one-year retention provision for processing records/data. Its application to transient biometric reference frames and deletion requests requires an explicit reviewed retention interpretation before the May 2027 phase; do not silently convert this into a new raw-photo archive. [Official final Rules, pages 26–27](https://www.meity.gov.in/static/uploads/2025/11/53450e6e5dc0bfa85ebd78686cadad39.pdf)

## Unverified until provisioned and piloted

- No AWS account permissions, effective opt-out setting, quota/cost configuration, KMS policy, STS role, or live liveness transaction was verified by this research.
- No actual shop Android camera/browser or controlled spoof test was performed.
- Provider threshold calibration, local employment-policy review, production retention decisions, and operational fallback training remain deployment prerequisites.
- A collection-based provider stores opaque templates in AWS, not exportable face descriptors in the app database. Provider migration requires reenrollment or a separately approved enrollment strategy.
